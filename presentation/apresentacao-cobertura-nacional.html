1. O novo escopo: cobertura nacional

O que o usuário pode explorar

  • Brasil → regiões → estados → municípios.
  • Filtros por doença, ano, mês, sexo e faixa etária.
  • Ranking e mapa sincronizados com o mesmo recorte consultado.
  • Seletores dependentes: uma região restringe os estados; um estado restringe os municípios.
  • Drill-down intramunicipal quando existe território oficial compatível.

Semântica da métrica

O produto apresenta notificações da unidade notificadora. A localização não deve ser interpretada automaticamente como residência ou local de infecção.

Note

“Cobertura nacional” significa disponibilidade do recorte epidemiológico nacional na aplicação. A cobertura territorial de distritos e bairros continua dependendo da existência de geometria e do vínculo oficial disponível.

Responsabilidade de cada camada

Camada Responsabilidade
Bronze Preservar a fonte recebida e o contexto da extração
Silver Normalizar nomes, tipos, códigos, datas e regras de qualidade
Gold/Serving Agregar notificações e materializar o recorte consultável

Java Expor contratos, validar filtros, aplicar autorização e consultar o banco
Front-end Apresentar mapas, rankings, filtros, sessão e fluxos administrativos

Pipeline: SINAN, CNES e IBGE

SINAN

  • Atualização idempotente por doença × ano.
  • Preservação dos arquivos de origem e manifestação do layout.
  • Deduplicação e validação antes da agregação.
  • Publicação somente após a carga concluir com sucesso.

CNES

  • Cadastro das unidades notificadoras e suas coordenadas.
  • Deduplicação por cd_unidade.
  • Vínculo da unidade com município, distrito e bairro quando possível.
  • Registros sem vínculo permanecem contabilizados, mas são marcados como não mapeados.

IBGE

  • Catálogo nacional de estados e municípios.
  • Malha oficial de municípios.
  • Malha de distritos do Estado do Rio de Janeiro.
  • Malha de bairros disponível somente onde a fonte oficial fornece geometria compatível.

4. PostgreSQL e metadados de publicação

O serving passou a guardar a identidade temporal da publicação. Isso evita que a consulta escolha uma linha arbitrária por meio de MAX quando o contrato exige a publicação exata.

WHERE disease_code = :disease
  AND reference_year = :year
  AND source_extracted_at = :sourceExtractedAt
  AND added_at = :addedAt

Benefícios

  • Reprodutibilidade de uma resposta já publicada.
  • Rastreabilidade entre arquivo SINAN, transformação e API.
  • Possibilidade de comparar duas publicações do mesmo recorte.
  • Exposição dos timestamps ao front-end para informar a origem dos dados.

Observabilidade

Pipeline → métricas Prometheus → dashboards/alertas Grafana
                         │
                         ├── execução e duração
                         ├── registros lidos e publicados
                         ├── falhas e status de carga
                         └── qualidade e cobertura territorial
  • Prometheus coleta as métricas expostas pela pipeline.
  • Grafana apresenta o estado das execuções e dimensões de publicação.
  • O PostgreSQL continua sendo a fonte dos dados epidemiológicos; Prometheus não substitui a consulta analítica.

Fluxo de uma consulta epidemiológica

HTTP request
  → controller valida entrada
  → service resolve escopo e publicação
  → repository executa SQL parametrizado
  → mapper converte linha em resultado
  → response devolve itens, total, cobertura e metadados
  • Controllers não acessam diretamente o PostgreSQL.
  • O domínio não depende de classes de persistência.
  • Repositórios isolam SQL, RowMapper e detalhes do JDBC.
  • O catálogo territorial resolve códigos IBGE e escopos nacionais.
  • Flyway versiona a evolução do schema.

Como o CI divide a confiança

pytest -m "not integration"
  → regras rápidas e determinísticas

pytest -m integration + PostgreSQL 16
  → carga, migrations e consultas reais

Compose validation
  → db + pipeline + Prometheus + Pushgateway + Grafana
  → backup/restore + permissões + métricas + dashboards

Além dos testes funcionais, a pipeline usa fixtures Parquet, CSV, JSON, XLS e banco temporário para reproduzir contratos sem depender sempre de uma fonte externa. O objetivo é testar tanto a transformação quanto a publicação operacional.

Testes cruzados entre pipeline e Java

fixture / execução da pipeline
          ↓
PostgreSQL + migrations
          ↓
Java integration test
          ↓
contrato HTTP / resposta do dashboard
  • A pipeline testa se a publicação chega ao schema esperado.
  • O Java testa se consegue localizar a publicação corrente por doença, ano e timestamps.
  • Os testes verificam filtros nacionais, recortes territoriais e totais.
  • A identificação temporal impede que uma consulta misture snapshots.
  • A validação de Compose confirma que observabilidade e banco podem subir juntos.

Essa divisão evita um falso positivo em que a pipeline passa isoladamente, mas a API não consegue consumir o dado publicado.

Estratégias contra testes artificiais — dados

Um teste artificial verifica apenas que o código respondeu algo plausível. A NSS usa camadas de evidência para verificar que o resultado continua correto quando passa pelo banco, pelos contratos e pela operação real.

Dados representativos e invariantes

  • Fixtures Parquet, CSV, JSON, XLS e catálogos IBGE/CNES exercitam layouts e códigos reais.
  • Os testes verificam totais, deduplicação, schemas, códigos territoriais e linhas rejeitadas.
  • Testes negativos cobrem arquivo vazio, filtro inválido, município fora do escopo e publicação ausente.
  • Snapshots e oráculos SQL comparam resultados completos, não apenas HTTP 200.

Estratégias contra testes artificiais — contratos

Contratos entre componentes

fonte → transformação → serving → SQL → API → resposta

Uma etapa não é considerada suficiente isoladamente. A pipeline valida o schema publicado; o Java valida que encontra a publicação correta; os contratos HTTP validam filtros, totais, cobertura e metadados.

Banco e infraestrutura reais

  • Testes de integração usam PostgreSQL 16, migrations e carga transacional.
  • O Java usa Testcontainers para testar repositórios, autenticação e fluxos persistidos.
  • O CI sobe a stack Docker de observabilidade e valida Prometheus, Pushgateway e Grafana.
  • O backup é restaurado em outro banco e consultado novamente.

Controles contra testes que “passam por acaso”

  • PIT altera regras do analytics e exige mutation score e test strength mínimos de 80%.
  • ArchUnit impede que controllers contornem services e repositórios.
  • Checkstyle, PMD, Spotless e JaCoCo são gates, não relatórios opcionais.
  • O Compose valida permissões reais: o usuário Grafana consegue ler, mas não inserir.
  • Métricas são publicadas no Pushgateway e verificadas por labels de pipeline, camada, doença e ano.

Estratégias contra testes artificiais — reprodutibilidade

Reprodutibilidade e separação de ambientes

  • Unitários são rápidos e determinísticos; integrações são marcadas e executadas com serviços reais.
  • Dependências são fixadas por lockfiles, versões de imagem e fixtures versionadas.
  • O CI constrói a mesma imagem operacional que é validada no deployment.
  • Nenhuma credencial de produção é usada para fabricar um resultado de teste.

O objetivo não é eliminar mocks: é impedir que um mock seja a única evidência. Mocks permanecem úteis para isolar uma regra; banco, migrations, contratos e containers verificam se a regra funciona no sistema completo.

Mutação: mutmut na pipeline e PIT no Java

Cobertura de linhas responde “o código foi executado?”. Mutação responde “os testes perceberiam se a regra fosse alterada?”. As duas métricas são complementares.

Pipeline Python — mutmut

  • Executa mutações nos módulos críticos de app/pipeline.
  • O escopo inclui Bronze/Silver/Gold, carga, território, CNES, atualização, preflight, métricas e referências IBGE.
  • As fixtures oficiais são copiadas para o ambiente mutado e qualquer mudança nelas força os testes dependentes a rodar novamente.
  • A primeira rodada exclui testes de integração para não reinicializar PostgreSQL a cada mutante; essa é uma delimitação de custo, não uma alegação de que integração não importa.
  • O comando reproduzível é mutmut run, seguido de mutmut results.
  • A meta documentada é matar 95% dos mutantes. Essa métrica é separada da cobertura de linhas.

Java — PIT

  • Executa mutação com pitest-maven e suporte JUnit 5.
  • O escopo atual concentra-se em com.example.nss.analytics.application, com os testes correspondentes de analytics.
  • O CI roda:
./mvnw -B test-compile org.pitest:pitest-maven:mutationCoverage
  • O gate configurado exige mutation score mínimo de 80% e test strength mínimo de 80%.
  • O ciclo documentado alcançou 180 de 191 mutações mortas: 94% de mutation score e 96% de test strength.
  • Mutações sobreviventes são classificadas. Casos equivalentes, inalcançáveis ou puramente criptográficos não recebem testes artificiais só para elevar a porcentagem.

Diferença prática

mutmut → robustez das transformações e cargas Python
PIT     → robustez das regras Java de aplicação/analytics

Ambos alteram o código de propósito e verificam se a suíte falha quando uma decisão relevante é invertida. Isso revela testes que executam uma linha, mas não protegem seu comportamento.

6. Front-end: mapa, ranking e estado de navegação

O front-end usa React, TanStack Query, React Simple Maps e GeoJSON estático carregado sob demanda.

filtros → request epidemiológico → cache por escopo
                                ↓
                       mapa + ranking + contexto
  • A cor dos mapas usa escala dinâmica baseada nos valores visíveis.
  • O mapa de estados usa códigos IBGE numéricos, iguais aos retornados pela API.
  • Tela cheia mantém a navegação territorial; “Voltar” retorna apenas um nível.
  • A sessão é restaurada por refresh token após recarregar a página.
  • A apresentação de dados exibe a data de extração do SINAN quando fornecida.

Validação territorial do Estado do Rio de Janeiro

Resultado cartográfico

  • 92 municípios validados.
  • 300 polígonos oficiais de distritos.
  • Nenhum arquivo distrital vazio.
  • Bairros carregados somente nos municípios com geometria oficial disponível.
  • Municípios com uma única divisão distrital podem abrir diretamente no ranking de bairros.
  • Municípios com múltiplos distritos abrem primeiro o ranking distrital e expandem o bairro quando possível.

Consistência de retorno

bairro → distrito → município → estado RJ → Sudeste → Brasil

Ao voltar de um município, o estado de origem é preservado; não se retorna indevidamente à lista nacional de municípios.

Validação automatizada

O front-end possui testes de build e E2E para:

  • regiões, estados e municípios nacionais;
  • 92 municípios do RJ;
  • distritos e bairros conforme disponibilidade;
  • ranking e mapa usando o mesmo recorte;
  • filtros de mês, ano, doença, sexo e faixa etária;
  • navegação em tela cheia;
  • sessão, login, logout e rotas protegidas;
  • fluxos de administrador e primeiro acesso.

O CI do GitHub Actions executa lint, TypeScript, build, instalação do Chromium e a suíte de testes Playwright.

Tip

Uma consulta epidemiológica nacional, rastreável e navegável territorialmente, com a mesma identidade de dados entre pipeline, banco, API, mapa e ranking.

Limites conhecidos e evolução futura

  • A presença de dados epidemiológicos não cria automaticamente um polígono oficial de bairro.
  • O vínculo territorial depende da unidade notificadora e da qualidade das fontes IBGE/CNES.
  • Novas doenças exigem contrato de código, dicionário e validação do schema de origem.
  • A atualização contínua exigirá política de publicação, retenção e auditoria de snapshots.
